# 設計変更：「フォルダを選ぶ」から始まる公開前チェック

実施日: 2026-10-07

## 背景

実機テストで、次の3つが初心者には難しいと分かった。
- プロジェクトURLの入力
- PAT（アクセストークン）の作成
- ターミナルの操作

このツールの目的は「Supabaseを知っている人向けの診断ツール」ではない。**AIでアプリを作り始めた初心者が、公開前の危険な設定ミスを確認できるツール**にすることである。

## 1. 変更した設計

```
【変更前】 npx koukai-check → ターミナルで Project URL を入力 → PAT を入力 → Supabase 診断 → ブラウザでレポート

【変更後】 起動 → ブラウザの画面で「チェックするアプリのフォルダを選ぶ」
           → フォルダの中身から、使っている技術をローカルで自動判定
           → その技術に必要なチェックだけを表示
           → Supabase を使っている場合だけ「Supabase のチェックを始める」→ 既存の Supabase 診断へ
```

- **主な入口は画面（ブラウザ）**：`npx koukai-check`（引数なし）で、127.0.0.1 のローカル画面が開く。操作はすべて画面で行う。
- **CLIは開発用**：従来の流れは `npx koukai-check supabase …` に移した。互換のため、`--project` や `--from-file` などの従来のオプションを付けた場合もCLIで動く。
- **Supabaseを使っていなければ、Supabaseの画面は出さない**：
  - ホーム画面とフッターに Supabase の名前を出さない。
  - URLを直接開いても、Supabase の画面へは進めない（チェック結果へ戻す）。
- **方針は維持した**：
  - 作者のサーバーへは送信しない。テレメトリはない。
  - フォルダの中身は読むだけで、書き換えない。自動修正もしない。
  - 実行時の依存パッケージは0個のまま。

### モジュール構成（追加分だけ）

```
src/detect/   技術の判定（読み取り専用）
  scan.ts       フォルダの走査。package.json・設定ファイル・.env の変数名から判定する
  env.ts        .env の読み取り（外へ出すのは変数名だけ）
  gitignore.ts  .env が Git の管理対象から外れているかの簡易判定
src/checks/
  build.ts      判定結果から、表示するチェックだけを組み立てる（データ駆動）
src/app/      一般ユーザー向けの画面
  server.ts     127.0.0.1 だけで動く画面用サーバー（ルーティング・CSRF対策）
  pages.ts      画面のHTML（ホーム／チェック結果／Supabaseのトークン入力／メッセージ）
  folder-picker.ts  OS標準の「フォルダを選ぶ」画面を開く
  run.ts        起動・終了
src/cli/mode.ts 起動方法の振り分け（画面 / 開発用CLI / ヘルプ）
```

既存のファイルへの変更は最小限に留めた。
- `report/html.ts`：任意の「戻る」リンクとフッター文言を追加し、スタイルを `export` した。何も指定しなければ従来どおりの出力になる。
- `report/open-browser.ts`：URLの末尾の `/` を許可した。
- `cli/index.ts`：起動方法の振り分けを追加した。
- `cli/texts.ts`：ヘルプの表記を変えた。

## 2. 実装内容

### 技術の自動判定（`detect/`）

| 判定する技術 | 根拠 |
|---|---|
| Supabase | `@supabase/supabase-js` などのパッケージ、`supabase/config.toml`、`SUPABASE` を含む環境変数名 |
| Firebase | `firebase` / `@react-native-firebase/*` などのパッケージ、`firebase.json`、`google-services.json`、`GoogleService-Info.plist`、`firestore.rules`、`FIREBASE` を含む環境変数名 |
| Expo | `expo` パッケージ、`"expo"` を含む `app.json`、`app.config.*`、`eas.json` |
| React Native | `react-native` パッケージ |
| Next.js | `next` パッケージ、`next.config.*` |
| 外部API | OpenAI / Anthropic / Gemini / Stripe / Resend / Twilio など18種類のSDK、`OPENAI` や `STRIPE` などを含む環境変数名 |
| .env | `.env` と `.env.*` のファイル |

- **走査範囲の制限**：
  - 読み取りのみで、深さ4まで、最大20,000件、1ファイルは1MBまで。
  - `node_modules`、`.git`、`.next`、`dist` などは読まない。
  - シンボリックリンクはたどらない（選んだフォルダの外を読まないため）。
  - サブフォルダの `package.json` も読むので、モノレポにも対応する。
- **`.env` の扱い**：外へ出す（画面に出す・保持する）のは**変数名だけ**。値を見るのは次の2つの判定のためだけで、判定が終わったら捨てる。
  1. `SUPABASE_URL` などの値（`https://<ref>.supabase.co`）から、**プロジェクトIDを自動で取り出す**（URLを入力する手間をなくすため）。
  2. `NEXT_PUBLIC_` や `EXPO_PUBLIC_` などの**公開用の変数**に、秘密のキーの形の値が入っていないか：
     - `sb_secret_…`
     - service_role の JWT
     - `sk-…`、`sk_live_…`
     - anon キーなど公開してよいキーは問題にしない。

### 表示するチェック（`checks/`）

| チェック | 出す条件 | 種類 |
|---|---|---|
| Supabase のデータベース設定を確認する | Supabase を使っている | 🔵 既存診断へ進む |
| アプリに埋め込まれる変数に、秘密のキーが入っている可能性 | 公開用の変数の値が秘密のキーの形 | 🔴 自動で見つかった |
| 公開される変数に、秘密情報らしい名前 | 公開用の変数の名前に SECRET や SERVICE_ROLE などを含む | 🟠 自動で見つかった |
| .env が Git の管理対象から外れていない | `.gitignore` で除外されていない | 🟠 自動で見つかった（除外されていれば ✅） |
| Firebase のセキュリティルール | Firebase を使っている | 📘 ヒント（自動チェックは準備中） |
| スマホアプリに入れたキーは取り出せる | Expo / React Native | 📘 ヒント |
| NEXT_PUBLIC_ はブラウザから見える | Next.js | 📘 ヒント |
| 外部サービスのキーはサーバー側だけで | 外部APIを使っている | 📘 ヒント（検出したサービス名を表示） |

判定できなかった技術のチェックは出さない。

### 画面（`app/`）

- **ホーム**：「チェックするアプリのフォルダを選ぶ」ボタンで、OS標準のフォルダ選択画面を開く。
  - Windows：PowerShell の FolderBrowserDialog（最前面に表示）
  - macOS：osascript
  - Linux：zenity → kdialog
  - 開けない場合は、パスを貼り付ける欄に切り替える。
- **チェック結果**：使われている技術と、必要なチェックを、重要なものから順に表示する。判定の根拠は「技術的な詳細」に折りたたむ。
- **Supabase**：
  - プロジェクトIDは `.env` から自動で入る（複数ある場合は選ぶ。見つからなければURLを貼り付ける）。
  - トークンの作り方を4ステップで案内する。
  - トークンは**パスワード欄**に貼るだけ。
- **安全対策**（既存のレポートと同じ水準）：
  - 127.0.0.1 だけで待ち受ける。URLには128ビットの乱数を付ける。Hostヘッダーを検査する。
  - CSP は外部への接続を禁止し、フォーム送信は同じサーバーへだけ許可する。
  - POST は、Origin が自分自身で、かつフォームに埋めた乱数（csrf）が一致するときだけ受け付ける。
  - 本文の上限は16KB。
  - トークンは POST の本文でだけ受け取り、URL・画面・ログには出さない。
  - 「終了する」ボタン、Ctrl+C、または30分使われなければ終了する。

## 3. 既存 Supabase 診断の再利用方法

既存の Supabase 診断のコードは**変更していない**。画面のサーバーから、次のように呼び出しているだけである。

```
app/server.ts（POST supabase/run）
  → supabase/client.ts   createManagementClient(token).getSecurityAdvisors(ref)   … 取得（Phase 1）
  → diagnostics/classify.ts  buildDiagnosticReport(result, { token: describeToken(token) }) … 分類・日本語化（Phase 2）
  → report/html.ts       renderReportHtml(report, { backLink, footerNote })        … レポートHTML（Phase 3）
  → 作ったレポートをメモリに置き、/report/<id> で表示（「HTMLとして保存」も従来どおり使える）
```

- エラーの案内も既存の `explainError` を使う（無効なトークン、権限不足、429、ネットワークなど）。
- Phase 4 の安全対策（通信先の固定・リダイレクトを追わない・応答サイズの上限・XSS対策・リンクの制限）は、そのまま効く。
- 開発用CLI（`koukai-check supabase`）も同じモジュールを使う。

## 4. 初心者が実際に操作する流れ

1. 起動する（現時点では `npx koukai-check`。最終的にはダブルクリック：§5）。
2. ブラウザで「公開前チェック」の画面が開く。
3. **「チェックするアプリのフォルダを選ぶ」**を押し、OSのフォルダ選択画面でアプリのフォルダを選ぶ。
4. 「使われている技術」と「このアプリに必要なチェック」が表示される。例：
   - 🔴 アプリに埋め込まれる変数に、秘密のキーが入っている可能性があります
   - 🟠 .env ファイルが Git の管理対象から外れていません
   - 🔵 Supabase のデータベース設定を確認する → **［Supabase のチェックを始める］**
   - 📘 スマホアプリに入れたキーは、誰でも取り出せます
5. （Supabase を使っている場合だけ）案内に沿ってトークンを作り、貼り付けて **［チェックする］** を押す。プロジェクトは自動で選ばれている。
6. 既存の日本語レポートが表示され、「AIに修正を頼む指示をコピー」が使える。「フォルダのチェック結果に戻る」で戻れる。
7. 使い終わったら **［終了する］** を押す。

ターミナルで入力する操作はない（起動コマンドを除く）。

## 5. 未実装の項目

| 項目 | 内容 |
|---|---|
| **Windows でダブルクリックで起動** | まだ `npx koukai-check`（Node.js 22 以上が必要）での起動。次の段階で、Node.js の Single Executable Applications（SEA）を使って1つの `.exe` にまとめることを想定している。署名の有無や SmartScreen の警告への対応を検討する必要がある |
| ブラウザを使わない画面 | 現在はローカルのブラウザ画面。専用のウィンドウ（Electron など）は依存パッケージが増えるため、まだ採用していない |
| Firebase のルールの自動チェック | 現在はヒントを表示するだけ |
| ソースコード中のキーの直書き検出 | `.env` と設定ファイルしか見ていない（`src/` 内に書かれた `sk-…` などは未検出） |
| Git の履歴にキーが残っていないか | 未対応（`.gitignore` の判定のみ） |
| Expo の `app.json` の `extra` にあるキー | Supabase のURLの抽出だけ対応 |
| Supabase のトークン作成の手間 | まだ PAT を手で作る必要がある。OAuth で連携する方式は将来の検討事項（OAuthアプリの登録や client secret の扱いが課題） |
| その他の技術 | Vercel、Clerk、Prisma など |

## 6. 次に確認すべきこと

1. **Windows の実機**：
   - フォルダ選択画面がブラウザの手前に出るか（TopMost を指定済み）。
   - 日本語を含むパス（`C:\Users\山田\…`）で動くか。
   - PowerShell の実行ポリシーで止められないか（`-ExecutionPolicy Bypass` を指定済み）。
2. **macOS の実機**：
   - osascript のダイアログ。
   - 初回に「ターミナルがフォルダへのアクセスを求めています」という許可が出るかどうか。
3. **実際のAIで作られたプロジェクト（Expo + Supabase、Next.js + Supabase、Firebase）で判定が合っているか**：誤検出や見逃しがないか。
4. **初心者による操作テスト**：
   - 「フォルダを選ぶ」で迷わないか。
   - どのフォルダを選べばよいか分かるか（package.json のあるフォルダ）。
   - トークン作成の案内で詰まらないか。
5. **実APIでのE2E**（Phase 4 から継続）：`docs/manual-e2e-check.md`。画面からの流れでも実施する。
6. **ダブルクリックで起動する方式の検証**：SEA でまとめた `.exe` のサイズ、ウイルス対策ソフトの誤検知、署名。

## テスト

`npm test`：**218件すべて通過**。
- 内訳：既存189件に、`app.test.ts` の28件と、`e2e.test.ts` に追加した1件を加えた。
- 主な追加分：
  - 起動方法の振り分け
  - `.env` の値を保持しないこと
  - 秘密のキーの形の判定
  - `.gitignore` の判定
  - 技術の判定（Expo+Supabase、Next.js+Firebase、何もない場合、モノレポ、`node_modules` を読まない、シンボリックリンクをたどらない、件数の上限）
  - 必要なチェックだけを出すこと（Supabase を使っていなければSupabaseのチェックを出さない）
  - フォルダ選択画面のコマンド
  - 画面のサーバー（CSRF・Origin・Host・413・XSSを含むフォルダ名・`.env` の値とトークンを画面に出さない・Supabaseの画面への直接アクセスを拒否する・レポートの表示と保存・終了）
  - 実際のプロセスを起動して「終了する」で終了コード0になること
- 静的監査の許可リストに、`app/server.ts`（待ち受け）と `app/folder-picker.ts`（子プロセス）を明示的に追加した。

実際のブラウザ（Chromium）で、次の流れを確認した。
- 操作の流れ：ホーム → フォルダを選ぶ（この環境では開けないため、パスの貼り付けに切り替わる）→ 判定結果 → Supabase → トークン入力 → エラー案内（この環境では api.supabase.com へ接続できない）→ 戻る → 終了
- 通信は 127.0.0.1 だけだった。
- コンソールエラーは0件だった。
- `.env` の値とトークンは画面に出なかった。

途中で見つけて直した不具合：`Referrer-Policy: no-referrer` だと、ブラウザがフォーム送信で `Origin: null` を送るため、CSRF対策で弾かれていた。アプリ画面だけ `same-origin` に変更し、テストを追加した。
