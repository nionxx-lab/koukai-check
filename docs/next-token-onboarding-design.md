# 次フェーズ候補（設計案）：Supabase のアクセストークン作成を、初心者にも簡単にする

作成日: 2026-10-08
状態: **A ＋ B は Phase 4.8 で実装した**（`docs/phase4.8-token-onboarding.md`）。C は公式の仕様が見つからなかったため実装していない。D（OAuth）は、ローカルで配布するアプリでは client secret を安全に持てないため見送り。

---

## 1. いまの流れと、つまずきやすい所

現在の画面（`src/app/pages.ts` の `supabaseTokenPage`）は、4行の手順を文字で案内し、パスワード欄に貼り付けてもらう。

```
[チェック結果] → 「Supabase のチェックを始める」
  → 手順を読む → リンクで Supabase のトークンのページを開く（既定のブラウザ）
  → ログイン → 新しいトークン → 種類・対象のプロジェクト・権限・有効期限を選ぶ → 作成 → コピー
  → 公開前チェックのウィンドウに戻る → 貼り付け → チェックする
```

初心者がつまずきそうな所（想定。§6 の利用者テストで確かめる）：

| # | つまずき | 起きること |
|---|---|---|
| T1 | 「アクセストークン」が何か分からない／危なくないか不安 | ここで離脱する |
| T2 | トークンの種類（Scoped と、権限の広い従来型）の違いが分からない | 権限の広い従来型を作ってしまう |
| T3 | 権限の一覧が長く、「Advisors: Read」を見つけられない | 全部に印を付ける、または何も付けずに作る |
| T4 | 対象のプロジェクトを選び間違える | 権限不足のエラー、または別のプロジェクトを診断 |
| T5 | 作成直後にしか表示されない文字列を、コピーせずに閉じる | 作り直しになる |
| T6 | ブラウザと公開前チェックのウィンドウの行き来で迷う | 貼り付ける場所が分からない |
| T7 | 権限不足・無効と言われても、どこを直せばよいか分からない | 何度も作り直す |
| T8 | 使い終わったトークンを消さない | 不要な認証情報が残る |

## 2. 守ること（今までの方針から変えない）

- 作者のサーバーを作らない・経由しない。テレメトリを入れない。
- トークンは保存しない（ファイル・ログ・画面・URL に出さない）。
- 読み取り専用・最小権限（対象のプロジェクトだけ、Advisors: Read だけ）を勧める。
- Supabase のダッシュボードを自動操作したり、画面を読み取ったり（スクレイピング）しない。
- データベースのパスワードや、ほかのツールが保存した認証情報（Supabase CLI のログイン情報など）を読まない。
- クリップボードを勝手に読まない（貼り付けは利用者の操作で行う）。

## 3. 方式の候補

| 案 | 内容 | 初心者の手間 | 新しいリスク | 実現できるか |
|---|---|---|---|---|
| **A. 手順の画面を、1ステップずつの案内にする** | 「トークンとは」→「ページを開く」→「この3つを選ぶ」→「コピー」→「貼り付け」を、図つきの小さな画面で順に案内する。今いるステップを強調する | 中（手順は同じだが迷いにくい） | なし | ◎ 今の仕組みのまま |
| **B. 貼り付けた瞬間の確認と、エラーごとの具体的な案内** | 貼り付け時に形を確認（`sbp_fc` → Scoped、`sbp_` → 従来型の警告、空白・全角・途中切れの検出）。エラーは「Advisors: Read が付いていません」「別のプロジェクト用のトークンです」のように、直す場所を1つだけ示す | 小（作り直しが減る） | なし | ◎（エラーの種類は今も判定している。§5 で実際の応答を確認） |
| **C. ダッシュボードの URL に、作成時の選択を含めて開く** | 名前・対象のプロジェクト・権限が最初から選ばれた状態でトークン作成画面を開く | 小 | なし | **？** Supabase がそのような URL に対応しているか不明。**対応していなければ採らない**（推測で作らない） |
| **D. 「Supabase でログインして許可する」（OAuth）** | ボタンを押すと既定のブラウザで Supabase の許可画面が開き、「許可」を押すとこのPCの 127.0.0.1 に戻ってくる。トークンのコピーと貼り付けがなくなる | **最小** | 中〜大（下記） | **？** 要調査 |
| E. Supabase CLI のログイン情報を読む | `supabase login` で保存された認証情報を使う | 小（CLI を入れている人だけ） | 大：権限の広い認証情報をディスクから読む | ×（方針に反する。採らない） |

### 案 D（OAuth）の検討メモ

利点：コピー・貼り付け・権限の選択がなくなり、T2〜T6 がほぼ解消する。

採るには、次をすべて満たす必要がある（§5 で確認する）：
1. **作者のサーバーなしで完結すること。** 許可のあとの戻り先を `http://127.0.0.1:<port>/…`（このPCの中）にでき、PKCE だけで（秘密の鍵を exe に埋め込まずに）トークンを受け取れること。秘密の鍵が必要なら、exe に入れた鍵は秘密にならないため採らない。
2. **権限を十分に絞れること。** Security Advisor に必要な範囲（`database:read` と推定）が、データベースの中身や他の設定まで読める広さかどうか。対象を**プロジェクト単位**に絞れず組織全体になる場合、今の「プロジェクト1つ・Advisors: Read だけ」より権限が広がる。
3. **利用者に見える「許可する相手」が作者のアプリになること**の受け止め。許可画面にはアプリ名と作者が出る。作者のサーバーへは何も送らないが、「作者のアプリに権限を渡す」ように見える。説明と、許可の取り消し方の案内が必要。
4. 受け取ったトークン（と更新用のトークン）を**保存しない**運用にできること。毎回許可してもらう形でよいか。
5. OAuth アプリの登録・審査・維持（作者側の作業）が現実的であること。

この5つのうち1つでも満たせなければ、D は採らない。

## 4. 推奨

**次フェーズでは「A ＋ B」を実装し、C と D は調査だけ行う。**

理由：
- A と B は、今の安全の仕組み（127.0.0.1・保存しない・最小権限）をまったく変えずに、つまずき T1〜T8 の多くに効く。
- C は、Supabase が対応していれば A に組み込むだけで手間がさらに減る。対応していなければ何もしない。
- D は最も簡単になるが、権限の広さ・作者のアプリとして許可を受ける形・秘密の鍵の扱いの3点で、今より安全性が下がる可能性がある。調査の結果を見てから、別のフェーズで判断する。

### A ＋ B の画面案（文章だけのスケッチ）

```
┌ 公開前チェック ─────────────────────────────────────┐
│ ← チェック結果に戻る                                   │
│ Supabase のデータベース設定を確認する                  │
│                                                        │
│ ステップ 1 / 4  アクセストークンについて                │
│  ・Supabase に「診断の結果だけを見せてください」と      │
│    お願いするための、合言葉のようなものです。          │
│  ・このあと作るトークンでは、データの中身は読めません。│
│  ・このPCの中でだけ使い、保存しません。                │
│                               [ 次へ ]                 │
├────────────────────────────────────────────────────────┤
│ ステップ 2 / 4  Supabase でトークンを作る              │
│  [ Supabase のトークンのページを開く ]（ブラウザで開く） │
│  作成画面で、次の3つだけを選んでください：             │
│   ✓ 種類：Scoped（範囲を絞ったもの）                   │
│   ✓ 対象：abcdefghijklmnopqrst（このアプリのプロジェクト）│
│   ✓ 権限：Advisors → Read                              │
│   ✓ 有効期限：いちばん短いもの                          │
│  ※ 作成後に表示される sbp_ で始まる文字列は、           │
│    その画面を閉じると二度と表示されません。先にコピー。 │
│                               [ コピーしました ]       │
├────────────────────────────────────────────────────────┤
│ ステップ 3 / 4  貼り付ける                              │
│  [ ●●●●●●●●●●●●●●●● ]   ← Ctrl+V または右クリック→貼り付け │
│  ✓ Scoped トークンの形です                              │
│                               [ チェックする ]         │
├────────────────────────────────────────────────────────┤
│ ステップ 4 / 4（結果のあと）  トークンを片付ける        │
│  チェックが終わったら、作ったトークンは削除できます。  │
│  [ Supabase のトークンのページを開く ]                  │
└────────────────────────────────────────────────────────┘
```

- 対象のプロジェクトID（`abcdefghijklmnopqrst`）は、今と同じくアプリの設定ファイルから見つけたものを表示する（選び間違い T4 の対策）。
- 図は、ダッシュボードの画面写真ではなく、**簡単な図と文字**にする（Supabase の画面が変わっても古くなりにくい）。「画面が違う場合」の補足を1行入れる。
- 貼り付け時の確認（B）は画面の中だけで行い、Supabase には「チェックする」を押すまで問い合わせない。表示するのは種類の判定結果だけで、トークンの文字は表示しない。

### B のエラー案内の対応表（案）

| 状況 | 判定のしかた | 表示（案） |
|---|---|---|
| 空白・改行・全角が混ざっている | 貼り付け時 | 自動で取り除き、「余分な空白を取り除きました」と表示 |
| `sbp_` で始まらない | 貼り付け時 | 「Supabase のアクセストークンではないようです（anon key や service_role key ではありません）」 |
| 従来型（`sbp_` だが `sbp_fc` ではない） | 貼り付け時 | 「権限の広いトークンです。Scoped で作り直すことをおすすめします」（続行は可能） |
| 無効（401 想定） | 問い合わせ後 | 「トークンが無効です。コピーが途中で切れていないか、削除していないか確認してください」 |
| 権限不足（403 想定） | 問い合わせ後 | 「このトークンに Advisors: Read が付いていないか、対象のプロジェクトが違います」＋ステップ2へ戻るボタン |
| プロジェクトが見つからない（404 想定） | 問い合わせ後 | 「このトークンでは、プロジェクト abcdef… を見られません。対象のプロジェクトを確認してください」 |

※ 401／403／404 の対応は、`manual-e2e-check.md` の 5-1〜5-4 で実際の応答を記録してから確定する（現時点では未記録）。

## 5. 実装の前に、Supabase 側で確かめること

| # | 確かめること | 使う案 |
|---|---|---|
| S1 | 現在のトークン作成画面の表記（種類の名前、権限の一覧での「Advisors」の表記、有効期限の選択肢、プロジェクトの選び方） | A |
| S2 | 作成画面を、選択済みの状態で開ける URL があるか（公式ドキュメントに記載があるものだけ使う） | C |
| S3 | 無効・権限不足・別プロジェクトのときの、実際の HTTP ステータスとエラー本文（`manual-e2e-check.md` 5-1〜5-4） | B |
| S4 | OAuth：127.0.0.1 への戻り先、PKCE のみでのトークン取得、秘密の鍵の要否 | D |
| S5 | OAuth：Security Advisor の取得に必要な範囲と、その範囲で読めるもの。プロジェクト単位に絞れるか | D |
| S6 | OAuth：アプリの登録・公開の手続き、許可画面に出る内容、利用者による取り消し方法 | D |

## 6. 効果の確かめ方（実装後）

作者のサーバーやテレメトリは使わないため、**数人の初心者に実際に使ってもらう利用者テスト**で確かめる。

- 「Supabase のチェックを始める」からレポートが出るまでの時間（目安：5分以内）。
- 途中で手が止まった場所と、作り直した回数。
- 従来型（権限の広い）トークンを作ってしまった人の数。
- チェック後にトークンを削除した人の数。

## 7. やらないこと（このフェーズの範囲外）

- 新しい診断項目の追加。
- トークンの保存・自動入力・自動での作成。
- 作者のサーバー・テレメトリ・解析。
- Supabase のダッシュボードの自動操作や画面の読み取り。
