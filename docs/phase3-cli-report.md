## 1. 実際の利用フロー

```
$ npx koukai-check

このツールは、Supabaseの認証情報や診断結果を作者のサーバーへ送信しません。診断はこのPC上で行います。

診断するプロジェクトを指定してください。（ダッシュボードのURL か プロジェクトID）

Supabaseのアクセストークンを貼り付けてください（入力した文字は表示されません）。

アクセストークン: ********（何も表示されない）

Supabaseの設定を確認しています...

http://127.0.0.1:41939/r/8fac96e7b9df0d30689854140787a67b
```

## 3. HTMLレポートの構成

1. **見出し**：公開前チェック結果・プロジェクトID
2. **総合判定**（大きく表示）
   - 危険が1件以上：「修正してから公開することをおすすめします」
   - 危険は0件で、要確認がある：「いくつか確認してから公開することをおすすめします」
   - どちらも0件：「大きな問題は見つかりませんでした」
   - 確認できなかった項目だけがある：「大きな問題は見つかりませんでしたが、確認できなかった項目があります」
   - 「安全です」とは書かない。
3. **件数**：🔴 危険 / 🟠 要確認 / 🔵 参考
4. **取得時刻**（日本時間）：時刻が1つなら「○時点の」、複数なら「A 〜 B の」、ない場合は「○に取得した」と表示する。
5. **注意書き**（常に表示）：「このツールですべてのセキュリティ問題を検出できるわけではありません。…」
6. **確認できなかった項目がある場合の注意**：「この診断結果には確認できなかった項目があります。「問題なし」とは判断しないでください。」と理由を表示する（読み取れなかった件数、実行できなかった診断、未対応の項目名）。
7. **Legacyトークンの警告**（該当する場合）
8. **診断カード**：危険 → 要確認 → 参考 の見出しごとに並べる。各カードの内容は次のとおり。
   - 危険度、日本語タイトル、対象（`public.profiles`（テーブル）など）
   - なぜ問題なのか、公開前にどうすべきか、修正方針
   - **「AIに修正を頼む指示をコピー」**（押すと「コピーしました」と表示）と、「指示の内容を見る」（折りたたみ）
   - Supabase公式の解説へのリンク（https のみ、新しいタブで開く）
   - 同じ対象への別の指摘へのリンク（カードは統合せず、意味を保つ）
   - 「技術的な詳細を見る」（折りたたみ）：公式の重要度・英語の説明・分類理由・元データのJSON
9. **フッター**
   - プライバシー表示（指示どおりの文言）
   - 「このレポートをHTMLとして保存」と、保存したファイルにプロジェクトの情報が含まれる旨の注意
   - サーバーが終了してもページは見られること
- デザインは、システムフォント、左端の色帯で危険度を示すカード、余白を多めにした読みやすさ重視。ダークモードにも対応する。外部のフォントや画像は使わない。

## 4. サーバーの起動・終了方式

- **起動**：診断が終わってから `127.0.0.1` で待ち受ける（ポートはOSが空き番号を選ぶ）。URLは `http://127.0.0.1:<port>/r/<128ビットの乱数>`。
- **終了**：
  1. **Ctrl+C（SIGINT / SIGTERM）** で即座に終了する。
  2. **最後にレポートが表示されてから30分たつと自動で終了する**（ブラウザで再読み込みや保存をすると延長される）。
  - 404や403になったアクセスでは延長しない。他のプロセスが勝手に延長し続けられないようにするため。
- **「見ている最中に消える」ことを避ける理由**：レポートは外部のリソースを使わない1ファイルのHTMLなので、サーバーが止まってもブラウザで表示中のページはそのまま残り、コピーボタンも使える。実際のブラウザで、サーバーを止めた後も表示が残ることを確認した。できなくなるのは再読み込みと保存リンクだけで、そのことはページとターミナルの両方に表示している。
- 起動からの経過時間で一律に止める方式（前回の実装では60分）はやめた。
- **HTMLとして保存**（指示書 §17）：`?download=1` のとき、同じHTMLを `Content-Disposition: attachment` で返すだけにした。新しい情報は含めず、自動では保存しない。保存したファイルは `file://` で開いてもスタイルとコピーが動くことを確認した（HTML内のCSPのnonceがそのまま使える）。PDFの生成はしていない。

## 5. HTML/XSS対策

- プロジェクト由来の文字列（テーブル名・スキーマ名・Advisor名・公式の説明・元データ）は、**すべて `escapeHtml` を通す**（`& < > " ' \``）。
  - バッククォートで囲まれた部分を `<code>` で表示する処理（`escapeWithInlineCode`）も、各部分をエスケープしてから組み立てる。
- リンクは **https のものだけ** 出す（`javascript:`、`data:`、`http:` は出さない）。
- 診断データを `<script>` の中に埋め込まない。AI修正指示は readonly の `<textarea>` にエスケープして入れ、スクリプトはその値を読むだけにしている。
- **CSP**：HTMLの `<meta>` とHTTPヘッダーの両方で設定する。
  - `default-src 'none'`、`style-src/script-src 'nonce-<起動ごとの乱数>'`、`img-src/font-src/connect-src 'none'`、`base-uri/form-action 'none'`
  - HTTPヘッダーにだけ `frame-ancestors 'none'` を付ける（metaタグでは無効なため）。
- そのほかのヘッダー：`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer`、`Cache-Control: no-store`、`Cross-Origin-Opener-Policy` と `Cross-Origin-Resource-Policy` を `same-origin` に。
- **ローカルサーバー**：
  - `127.0.0.1` だけで待ち受ける。
  - URLのパスは推測できない乱数にする。
  - Hostヘッダーが `127.0.0.1:<port>` か `localhost:<port>` 以外なら403を返す（DNSリバインディング対策）。
  - GETとHEAD以外は405を返す。
- 外部のCDN・フォント・画像・解析ツールは使わない。実際のブラウザで確認したところ、**通信はレポート本体の1回だけ**で、CSPの違反は0件だった。

## 6. トークンの保護方法

- 環境変数から読むか、入力した文字を表示しない形で入力してもらう（TTYでない場合は、エコーのないパイプからそのまま読む）。
- メモリ上でのみ扱い、**設定ファイル・ログ・ターミナル出力・HTMLには書かない**。HTMLを作る関数（レンダラー）にはトークンの値を渡さない（渡すのは `{kind, isBroadAccess, noticeJa}` だけ）。
- 通信先は `api.supabase.com` に固定している（Phase 1 から変更なし）。トークンは `Authorization` ヘッダーでだけ送る。
- 終了したら（Ctrl+C か自動終了）プロセスが終わり、メモリ上のトークンもなくなる。
- テストで確認していること：トークンの値が、ターミナル出力・エラー出力・配信するHTMLのどれにも含まれない。

## 8. 新しく見つかった問題（Phase 3 の中で修正済み）

1. **パイプ入力で2行目以降が失われる**：`ask()` のたびに入力の読み取り口を作り直していて、先に読み込まれた行が捨てられていた。TTYでない場合は1つを使い回すよう修正した。
2. **readline での Ctrl+C**：入力待ちの Ctrl+C が無視されていた。中断（終了コード130）として扱うよう修正した。
3. **CSPの `frame-ancestors` を metaタグに書いていた**：metaタグでは無効で、ブラウザが警告を出していた。HTTPヘッダーにだけ付けるよう変更した。
4. **タイトルのバッククォートがそのまま表示される**：Phase 2 の文面は対象名を `` `…` `` で囲んでいる。エスケープを保ったまま `<code>` で表示するよう変更した（AI修正指示はMarkdownのまま）。
5. **起動から60分で一律に終了していた**：「最後の表示から30分」方式に変更した（§4）。

未解決の注意点：
- Windows でのブラウザ起動（`cmd /c start "" <url>`）は、この環境では確認できていない。
- `[::1]` に接続できないことのテストは、IPv6が無効な環境では「待ち受けていない」以外の理由でも通ってしまう。LAN側のアドレスのテストは、LANのない環境では確認を省略する。

## 9. Phase 4 で確認すべき安全上の項目

1. **実際のTTYで入力文字が表示されないこと**：macOS Terminal、Windows Terminal / PowerShell / cmd、Linux。ペーストやバックスペース、日本語IMEがオンのときの入力も含めて確認する。
2. **ブラウザの自動起動**：macOS（`open`）、Windows（`cmd /c start`）、Linux（`xdg-open`）、WSL。起動に失敗したときにURLを表示するか。
3. **ローカルサーバー**：
   - ファイアウォールの警告が出ないか（127.0.0.1 のみなので出ない想定）。
   - 同じPCの別ユーザーから到達できるか（パスの乱数で緩和している）。
   - DNSリバインディングの実際の攻撃シナリオ。
   - 長時間放置したときの自動終了。
4. **エスケープの網羅**：診断定義の全文面と実際の応答の組み合わせで、不正な文字列を自動生成して試すテスト（ファジング）。
5. **CSPの実効性**：主要ブラウザ（Chrome / Edge / Safari / Firefox）で違反がないこと、保存したファイルでも有効であること。
6. **外部への通信がないこと**：OSレベルで通信を監視し、`api.supabase.com` 以外へ通信しないこと。
7. **トークンの残り方**：シェルの履歴（`SUPABASE_ACCESS_TOKEN=… npx` と書いた場合に履歴に残る件をREADMEで注意喚起するか）、プロセス一覧への露出、異常終了時の出力。
8. **配布物の点検**：`npm pack` の中身、依存パッケージが0個であること、`samples/` を含めるかの判断。
9. **保存したHTMLの扱い**：プロジェクトの情報を含むファイルを共有するリスクの説明が十分か。
